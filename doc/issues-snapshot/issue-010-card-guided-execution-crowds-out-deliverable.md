# issue-010: 照卡执行挤占交付本能——注入卡片致重复集分数连续下滑

- 状态：**open（用户决定：所有代码修改延迟到 C campaign 测试完成后）**
- 报告：2026-08-12（D3 数据 + 个案机制分析，监控发现+用户确认）
- 影响面：离线进化管线（蒸馏模板/验证闸门）+ 注入协议——**非单点 bug，是生产线设计缺陷**

## 现象

C campaign 重复集（实验臂，每日带记忆重跑同 20 任务）分数连续下滑：

| 日 | 均分 | 均请求/任务 | 升级率 |
|---|---|---|---|
| D1（空库） | 0.567 | 15.8 | 0% |
| D2（首轮卡） | 0.540 | 15.3 | 0% |
| D3（次轮卡） | 0.404 | 12.6 | 0% |

D3 降幅（-0.136）超出 D1 对照臂实测噪声地板（±0.04）。升级率全程 0%，与门控无关。

## 证据链

1. **逐任务定位**：task_00091（security_policy_assessment）D2 0.71 → D3 0.00。
2. **注入内容审查**（session 归档 tar 提取 custom_message）：注入的是高度相关的 Method 卡（"审计输入信任策略时，先用事件证据验证声称为真：①查文档状态②提取控制项③映射事件日志④核查配置⑤比对提案矛盾⑥写带证据附录的评估"）——**排除"碎片误导"假设**。
3. **judge 评分明细**（run.jsonl）：D3 分析质量获 judge 认可（识别出 CTL-002 矛盾、v1 draft 等），但 `automated.output_file_exists: 0.0`——**交付文件未写**，全部自动检查项归零。
4. **行为形态**：D3 该任务 11 请求（D2 为 16）——模型按卡执行完分析流程后提前收工，未产出交付物。全局同形态：轮数与分数同步下降。

## 根因（机制定性）

1. **蒸馏模板缺陷**：Method 卡只提炼"过程步骤"，未提炼"任务交付物要求"——卡片流程不完整（缺交付步骤）。
2. **验证闸门盲区**：卡片验证打分评估"程序合理性"，不验证"按卡执行能否产出交付物"——自评通过 ≠ 行为效用（B 阶段已预警，本次为实锤）。
3. **行为层**：卡片引导的固定流程替代了模型自主探索到交付的路径——"照卡执行挤占交付本能"。

## 延迟到 C 完成后的修复项（届时立项执行）

1. 蒸馏模板加"交付物清单"维度（每张 Method 卡必须含 deliverables 字段）
2. 验证闸门加"交付物产出"检查项（回放验证以交付物存在为必要条件之一）
3. 存量卡片重蒸馏或补充 deliverables
4. 回归测试：构造"分析完整但无交付"的轨迹，验证闸门能拦截此类卡片

## 当前处置

不中断 C campaign（判据为升级率而非分数；对照臂 D7 提供自然波动参照）；D4-D7 继续按预注册判据执行；本机制分析作为 C 报告核心章节的一手证据。
