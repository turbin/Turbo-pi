## 3. 臂设计与任务集

任务集沿用 C：QCB v1.1 99 任务，seed=42 确定性划分——**重复集 20（每日全跑）+ 新任务集 79 按日切片（D1..D7 各 11-12）**。同批同人同 seed，D/C 两阶段任务级可比。

**阶段一（D1 起，已开跑）：双臂**（experiment=当日库+注入开 / control=注入关，仅 D1/D7 跑对照——同 C 口径）。

**阶段二（交叉臂，待拍板）：库版本 × 注入 2×2**（X1 冻结库+开 / X2 当日库+开 / X3 当日库+关 / X4 冻结库+关；冻结 = D1 结束时空库快照，锁库不换载，--frozen-base-url 双实例）。差分口径预注册（交叉臂 plan §设计）：库演进 = X2−X1；即时注入 = X1−X4；sanity = X3−X4 ≈ 0。

**成本重估（pilot 实测）**：9B 单任务均 16.5min（omlx concurrency=1 串行瓶颈）——四臂每日 80 重复任务 + 12 新任务 ≈ 25h/天，串行不可行。**定案（用户 2026-08-19 方案 A）**：四臂仅跑 D2 与 D7 两天（其余天数双臂 experiment/control 口径不变），n=20 功效声明保住，日历 +1 天以内。被否方案：B 交叉臂重复集减半（n=10 功效声明需重写）；C omlx 并发扩容（改变生产口径且显存受限）。

## 4. 每日循环与监视

```
白天：campaign.py --day N（实验臂 [重复 20 + 新切片] + D1/D7 对照臂）
      → 8789 → 8787 gateway → omlx 9B（门控升级 DeepSeek，length<5% 门控）
      → 逐任务评分（judge=deepseek-v4-pro）
      → Langfuse 实时监视（gateway generation + 任务 span + qcb_score）
夜间：合成轨迹 → runDailyEvolution（当日库）→ 次日热库；库快照（snapshot_store，N=7）
门禁：跑批前置核验清单（AGENTS.md 约束）每日开跑前逐项过检
```

判据核算：`campaign.py --metrics`（含四臂时自动附交叉差分，T7 已交付）。对账链：run.jsonl.trace_ids ↔ model_runs ↔ session marker ↔ Langfuse trace（issue-015 修复后口径，create_trace_id(seed) 确定性 join）。
