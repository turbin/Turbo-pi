小模型长程规划、执行与隐私保护云规划

2026-08-25 对话综述 · 结合当前 Turbo-pi D 阶段工程证据与 14 个外部一手来源

结论先行：当前实验仍然有意义，但它主要证明“经验库和执行脚手架是否改善局部决策”，还没有证明小模型获得了稳定的长程规划能力。下一步最有价值的路线不是单纯堆记忆，而是把规划、执行、验证和升级拆开：以结构化子目标和滚动重规划降低有效任务跨度，用确定性验证器和任务级无进展门控控制错误扩散；先验证本地 27B 规划器 + 9B 执行器，再在隐私抽象层成熟后引入只看脱敏任务图的云端规划器。

二、逐项解释与文献证据

疑问 1：如果长规划能力不提升，当前实验还有意义吗？

“increasing horizon length alone constitutes a training bottleneck” [1]

解释：长程任务困难不只是“记得不够多”。交互步数增长会同时放大探索空间、延迟信用分配、错误累积和上下文污染。相关研究发现，仅增加训练任务的 horizon 就足以造成训练不稳定；把长任务拆成较短的可训练跨度，反而可能获得向长跨度泛化的能力。

所以当前实验仍有三类独立价值：第一，经验库可能改善局部工具选择、错误恢复和证据复用；第二，连续跑批正在暴露真正的瓶颈——规划、状态跟踪和停止条件；第三，它提供了以后比较“记忆 × 规划脚手架”的基线。

对当前工程的含义：不能把 active 卡数量增长等同于长规划能力增长。若 D7 仍未显示稳定提升，应把结论写成“经验积累机制有效运行，但端到端收益受规划瓶颈限制”，并继续做 issue-021 的 Memory × Scaffold 2×2，而不是判定整个实验无意义。

疑问 2：规划与执行分别依赖什么？为什么合法命令仍会失败？

“explicit separation of planning and execution” [2]

解释：规划依赖任务分解、因果/世界模型、跨步工作记忆、状态估计、替代方案搜索、进度监控和停止判断；执行更依赖指令遵循、工具语法、参数绑定、环境反馈理解和局部纠错。参数规模会提高表示容量和搜索质量，但不存在一个可单独调节的“规划参数”。上下文长度也只提供存储空间，并不自动带来正确的状态更新或信用分配。

命令“格式合法”与任务“语义正确”是两件事。模型可以连续产生可解析的 bash/tool call，却选错目录、重复检查同一状态、误读错误输出、遗漏交付物，最终耗尽回合。这正是当前 D1 证据显示的分离：1,369 个请求中 1,347 个以合法 tool_calls 结束，但仍有 23 个明显失败，且全部没有触发升级。

“predict the next single-step action to take” [4]

Fara 1.5 的设计说明一种实用取舍：执行模型每次只负责一个原子动作，把跨步组织、上下文管理和验证交给训练数据与 harness。这样不是让小模型“凭空更聪明”，而是减少每一步必须同时解决的问题数量。

疑问 4：业界已经取得了什么进展？

“codesigning the app, models, and the harness” [3]

共同趋势不是只训练一个更大的端到端模型，而是协同设计：

  • Microsoft 的 MagenticLite 使用约 14B 的 MagenticBrain 做规划、编码和委派，用 9B 级 Fara 做计算机操作，强调增量规划、上下文管理和子代理。
  • Fara 1.5 公布的 Online-Mind2Web/WebVoyager 分数随 4B、9B、27B 规模上升，说明模型容量仍重要；但其合成环境、教师、验证器和原子动作约束同样是结果的一部分，不能把进展归因于参数量。
  • EAGLET 把全局规划器作为可插拔模块，用合成计划、共识过滤和基于执行器能力增益的奖励训练，并报告比同类 RL 基线更低的训练成本。
  • Multi-Level Reasoning 采用高层子目标规划器与低层执行器交替运行，并用轻量 LoRA 与过程偏好优化提升稳定性。

“executor capability gain reward” [8]

“alternating plan--execute loop” [9]

综合判读：小模型已能在特定环境中通过分层、验证和强 harness 获得显著提升，但尚没有证据表明通用 9B 模型只靠记忆注入就能稳定处理开放式长程软件任务。业界进展更准确的表述是：系统把长程能力拆成可管理的模块后，小模型可以承担其中相当大的一部分。

疑问 5：外部模型何时升级？当前标准有效吗？

当前 gateway 的 evaluate_quality() 只在四类单响应条件下升级：

  1. 工具未声明、参数 JSON 非法、缺必填字段或顶层类型不符；
  2. finish_reason=length；
  3. 文本和工具调用同时为空；
  4. 调用方强制指定某工具，但模型没有调用。

判定：作为协议级安全门，它有效；作为任务级质量门，它无效。D1 对账确认 1,369/1,369 个 trace 完整、云升级确实为 0，但 23/23 个明显失败没有升级，MissedEscalationRate=100%。这说明它测到的是“响应是否可解析”，不是“任务是否在收敛”。[本地证据 A]

“central LLM dynamically breaks down tasks” [10]

任务级升级应放在 agent/harness 层，维护跨回合状态，而不是强塞进无状态的单请求格式门。建议先 shadow 记录以下信号：连续无状态推进、重复命令/近似状态循环、工具错误率、计划偏离、关键交付物缺失、剩余回合预算。用 D1—D7 轨迹离线回放预注册召回率、误报率、云成本与隐私风险，再决定上线阈值。

疑问 7：能否让云端规划、本地执行，同时不泄露具体数据？

“planning-oriented digital twin” [12]

可以，但只能承诺“最小化披露并可审计”，不能承诺绝对不泄露。关键是让云端看到一个规划数字孪生，而不是原始工作区：随机化对象 ID、能力图、依赖关系、允许动作、约束、完成谓词和抽象错误类别；文件内容、真实路径、凭据、命令输出和客户数据都留在本地。

反馈给云端的也只能是抽象状态，例如 PRECONDITION_FAILED(node_7)，而不是完整 stdout/stderr。每轮限制字段和累计披露预算；计划必须通过本地 schema、能力白名单、数据流检查和人类设定的高风险动作门。

“Indirect prompt injection attacks occur when adversaries remotely” [13]

主要风险：抽象层仍可能发生组合泄露；仓库中的恶意文本可能通过摘要进入规划提示，形成间接提示注入；云端计划也可能诱导本地执行器逐步读取或外传敏感信息。因此本地 gatekeeper 必须拥有最终权限，云端计划不能直接执行。

“Encrypted memory, isolated by hardware from other workloads” [14]

可信虚拟机、内存加密和远程证明可作为额外保护，使明文只在可验证的隔离环境中出现；但这类 confidential inference 仍处于演进阶段，不能替代最小披露、固定 schema、出站检查和日志审计。

三、针对当前工程的综合方案

  1. 先完成 D7 收口。保持 D1—D7 在线门控不变，防止破坏预注册可比性；把协议级升级率、AutonomousSuccessRate、MissedEscalationRate 联合报告。
  2. 执行 issue-021 的 2×2。比较 Memory on/off × structured plan-to-file on/off，直接回答收益来自记忆还是规划脚手架。
  3. 增加本地分层臂。27B 只产出结构化子目标、依赖和验收谓词；9B 每次执行一个原子步骤；每步由测试、文件存在性、退出码和状态 diff 验证。
  4. 建立任务级 shadow gate。先离线学习无进展、循环、工具失败、预算逼近和交付物缺失阈值；以教师可挽救率评估真正价值，不用“是否格式合法”代替质量。
  5. 再试隐私保护云规划。先用本地 27B 验证 Plan DSL 和抽象器；只有本地方案证明规划分层有效后，才让云模型读取脱敏任务图，并设置披露预算与本地 DLP gate。
  6. 最后做蒸馏/训练。把已验证的成功计划、子目标、验证结果和失败回退变成训练数据；避免在架构和标签尚不可靠时，把错误轨迹蒸馏进小模型。

建议的成功判据：在相同任务与预算下，功能成功率提高；平均回合数与重复调用率下降；任务级门控对“教师可挽救失败”的召回率提高且误报/成本在预算内；云规划输入通过自动 DLP 检查，且任何计划均不能绕过本地能力白名单。
