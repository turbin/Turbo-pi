## 坚持项详述

### F-03（落盘失败阻塞响应）——坚持：文档声明了取舍，但取舍的理由在失败模式下是假的

设计方答辩：`"宁失败不漏录"是刻意红线（记录不可关）……落盘失败会使请求失败，这是取舍而非疏忽；在线服务化时需重议。` §2.2 已写入该声明。

我接受"记录不可关"作为设计意图，但**反对把这条取舍描述为"宁失败不漏录"**，因为它在落盘失败的现场并不能兑现"不漏录"，反而同时保留两个坏结果。这是同一主题（落盘失败是否阻塞响应）下的更强论证，不是新主题：

1. **真实状态是三态，不是二态。** 答辩把选择表述为二选一："要么完整记录+成功响应，要么失败（=不漏录）"。实际代码路径是：session JSONL 用 `createWriteStream(path, {flags:"a"})` **边流式边追加**（`session-writer.ts`），header → messages → 逐个 `stream_event` 逐行写。磁盘在写到第 N 个事件时满，`writeLine()` throw，请求失败——但磁盘上已经留下了一个**合法 JSONL 前缀**（header + 前 N-1 个事件的完整行）。这不是"未记录"，而是"半截记录"。
2. **半截记录照样进学习回路。** `offline/pipeline.ts:parseSessionFile` 对每行 `try { JSON.parse } catch { continue }`，对合法前缀行照单全收。也就是说"宁失败不漏录"想要保护的进化进料，反而会被一条失败请求产生的截断轨迹污染——`collectTrajectories` 会把一个写到一半的任务当成完整轨迹交给三管线蒸馏。**取舍声称避免的"漏录/脏录"，在失败模式下照常发生。**
3. **失败还会被 harness 重试放大。** issue-008 沉淀的断点续跑/退避重试意味着：磁盘满时请求失败 → harness 重试 → 再写一段新前缀 → 更快耗尽磁盘 → 更多失败。落盘子系统故障不但切断在线响应，还加速自身存储耗竭。

**结论与诉求**：我不要求"响应继续、放弃记录"（那与"记录不可关"冲突）。我要求文档把这条取舍的措辞从"宁失败不漏录"改准为"落盘失败即失败，但可能留下截断 session，须由归档/ETL 显式剔除不完整 session"——即：承认失败模式是"半截记录 + 失败"，并把"ETL 跳过 `record_incomplete`/无终态条目的 session"列为 §7 台账的一个具体动作。当前 §2.2 的"而非静默漏录"表述给读者传达了"不会产生脏进料"的错误保证。

（补充证据：`proxy-handler.ts` 的 catch 分支在 `writeCustomEntry("error")` 时若再次 throw，`writer.close()` 不会执行、`openSessionPaths` 不释放——失败路径自身的清理也不可靠。）

### F-05（前置失败丢弃本地结果 / 默认预算 None）——坚持：429/422 fail-closed 会系统性污染核心 KPI，且 preflight 不校验

设计方答辩：403 维持 fail-closed（同意）；接受 422/429 与 403 语义不同，把"是否降级回本地"写入 §3.1 边界(1) 标为"待议"；默认预算 None 写入边界(3)。

我接受 403 维持 fail-closed，也接受"降级回本地是否合理"可以继续议。但**"待议"的表述漏掉了 429/422 fail-closed 的一个一级后果——它不是中性的可用性损失，而是直接压低本系统唯一用来论证"学生独立"的指标**。同一主题下的更强论证：

1. **429（预算耗尽）恰好精准删掉"升级事件"。** 升级率口径（§1）= per-任务日二元：任一请求升级即记 1。预算耗尽时，凡是"本地不合格、需要升级"的请求全部 429 失败，**不产生升级、也不产生本地接受**；而"本地合格"的请求完全不受影响继续通过。结果是：在预算耗尽的窗口内，升级率的分母里只剩本地合格请求，分子（升级次数）被人为清零。观测到的升级率**被系统性向下偏置**——而这正是"重复任务升级率趋近 0"的验收依据。预算耗尽不是让系统"停摆"，而是让系统"只记录那些证明学生独立的部分"。
2. **422（egress 未配置）同理且更隐蔽。** `config.py:81` `cloud_egress_allowed` 默认 False，若 channel 未显式打开 egress，所有升级请求 422。这不是运行时事故，而是**静态配置缺陷**——但 `preflight.py` 只校验 gateway `/v1/models` 指纹与 agent-server chain，**不校验该 channel 的 egress 开关与月度预算是否配置**。于是一个"忘了开 egress / 忘了设预算"的批次不会在批前被拦下，而是在整批运行中静默地把所有升级事件变成 422，等价于跑了一个"学生永不升级"的假象批次。issue-004/005 的教训（"观测缺口即盲区"）在此重演。
3. **默认预算 None 的下游**（边界(3)已承认"预算闸不生效"）与 (1) 叠加：设了预算 → 耗尽后 KPI 被污染；不设预算 → 成本闸失效。两种配置都没有一个"正确而可观测"的中间态。

**结论与诉求**：不要求立刻实现"降级回本地"（服务已知坏结果是可议的）。要求两件事落账：(a) §7 台账补一条"升级前置失败（422/429）会剔除升级事件、向下偏置升级率 KPI，需在指标核算中显式剔除或告警"；(b) preflight 增加 egress 开关与月度预算的批前校验（或至少文档声明该缺口）。这仍是 F-05 的原主题（前置失败的处理与默认配置），非新主题。
