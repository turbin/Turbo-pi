## 二、坚持项（更强论证）

### 二.1 F2 — "逐步独立"是不可测的因果命题：非目标排除权重更新，使"学习"与"注入即时示范"在判据体系中不可区分

**设计方已回应**：混淆因子已补声明；反驳"无判别力"全称，主张"趋势判据③ + D1/D7 对照差值 + 演进 4 基线"构成递进证据链。

**我承认的部分**："实验设计无能力区分"确系过强表述——它至少有弱判别力（能测出"注入开关的有无"与"门控漂移的量级"）。此全称撤回。

**坚持的新论证（结构层，非混淆因子枚举）**：

1. §1 非目标明确排除"token 级 RL 与权重更新"。因此学生模型参数在整个实验期间**恒定**。"逐步独立"这一能力命题，唯一可能的因果载体是经验库（harness），**不可能是学生能力增长**。
2. 由此产生一个判据体系无法自证的空白：**不存在任何"学习后摘除注入"的测量臂**。对照臂（injection off）仅在 D1/D7 各跑一次，且因权重冻结，对照臂在任一时点都是"同一裸模型"——它只能测"门控/环境随时间的漂移"（这是有价值的参照），**永远测不出"库变好后裸模型是否更独立"**（因为构造上不可能变好）。
3. 因此判据体系唯一可测的量是"注入后系统的升级率"，而升级率是**形式指标**（四规则：schema 有效/非空/非截断/强制工具存在）。"独立"是**任务能力**命题。两者之间无桥梁：一个学会了"永远输出 schema 合法、非空、不触 max_tokens、必带强制工具，但内容全错"的学生，升级率趋近 0，任务能力仍为零。设计没有测量点能排除这一情形。
4. 演进 4（纯 27B 基线重跑）测的是"裸能力在某一时点的水平"，不是"学习后的裸能力"——在无权重更新的前提下后者在物理上不存在。故演进 4 补得上"基线"，补不上"学习 vs 即时示范"的分解。

**结论**：设计方能证明的最强命题是"经验注入使系统（学生+库）的形式合规率与升级率改善"，而非文档 §1 声称的"学生逐步独立"。§1 目前只补了"混淆因子清单"，未补"目标命题与可测量之间的本体鸿沟"。建议 §1 把目标改写为"经验库+注入使 27B 在办公域的形式合规与升级率改善"这一**可证伪**表述，或显式声明"独立"在本设计中的操作化定义即"注入关闭下升级率"（而该口径当前仅 D1/D7 两个时点）。

### 二.2 F7 — 反驳证据"dormant 有存量"是 non-sequitur；闸门唯一分辨轴是"可见错误密度"，与"值得留下"正交

**设计方已回应**：接受"不验成败/交付物"，但反驳"近乎恒真"——dormant 池持续有存量候选被拦在闸外，说明闸门有实际拦截。

**我承认的部分**："近乎恒真"作为全称确系过强（至少在 Errors 标准上，充满可见错误信号的轨迹会被判低分）。撤回"任何多步轨迹都能过"的表述。

**坚持的新论证**：

1. **"dormant 有存量"不构成拦截证据**。`etl.ts` 把每条长度 >10 的 assistant/toolResult 句子以 `status='dormant', quality=0` 入库——dormant 是**默认插入态**，不是"被拒态"。晋升依赖 `runDormantRescore`，而 `scheduler.ts` 每批只复评最老 200 条；E5 实测单轮 ETL 插入 15,069 条 dormant。即：存量主要由"复评吞吐（200/批）<< 插入量"与"30 天 TTL 到期"解释，**绝大多数 dormant 从未被复评过**。要证明闸门有分辨力，必须给出"被复评候选中的通过率/拒绝率"——该数字设计方未提供，而它是 F7 唯一相关的事实。
2. **即便存在拒绝，拒绝轴与设计目的正交**。闸门三项标准之一 Errors = "trajectory 无错误信号"。一个**静默出错但结构干净**的轨迹（有计划、有验证、无 "Nothing happens"）在 Specification/Output 上都与 strawman 同分、在 Errors 上还优于"满篇失败信号"的轨迹，会击败 strawman 而被当作"成功经验"提取；而一个**真正完成任务但过程磕绊**（大量可见失败再恢复）的轨迹反而可能因错误信号密度被判低。即：闸门能分辨的是"过程是否干净"，不是"经验是否有助于完成任务"——这与 issue-010（照卡执行挤占交付）是同一个根，且比 issue-010 更底层：**闸门连"成败"这一维度都未被纳入，遑论"交付物"**。
3. §3.3 局限声明(3) 只写了"不验任务成败与交付物"，但未写明"其唯一可能的分辨信号是可见错误密度"。在"弱 ≠ 恒真"与"完全无判别力"之间，真实位置是"**判别力存在于一个与设计目标正交的轴上**"——这比设计方承认的"弱"更严重，值得在文档中如实定位。

### 二.3 F14 — 教师指导"升级单步混入"在实现中与错误步骤融合于同一轨迹，冷启动期正确示范不可分离

**设计方已回应**：澄清教师指导形态（升级单步混入 transcript + 裁判/蒸馏器），接受 prompt 错配入台账；反驳"循环依赖致不可启动"——C 换型 27B 后成功局比例上升，教师升级步骤本身提供局部正确示范。

**我承认的部分**：我 round 1 未下"不可启动"的全称结论，此推断撤回；27B 基线高于 gemma、升级步骤确实注入正确内容，均属实。

**坚持的新论证（实现层）**：

1. **教师示范与错误步骤在输入中被融合、不可分离**。`synthesize_campaign_sessions.py` 只把 campaign transcript 的 assistant 轮次逐条写出，**不写 provider 标记**；`pipeline.ts collectTrajectories → parseSessionFile` 把所有 assistant/toolResult 文本 `texts.join("\n")` 拼成**一条字符串**，无任何 student/teacher/胜负字段。教师升级单步与学生错误步骤在蒸馏输入中物理上不可区分。
2. 后果：蒸馏面对的是一个"混合轨迹整体"。F7 的 strawman 闸门对**整条**混合轨迹打分，`EXTRACTION_PROMPT` 对**整条**混合轨迹按 "successful trajectory" 提取卡片。设计方所称"教师升级步骤提供局部正确示范"因此不成立为**可用示范数据**——它只是混在一条可能失败轨迹里的噪声，既不能被单独识别为"教师正确步骤"，也不能被单独保留。
3. **冷启动期此问题最严重**：经验库为空 → 学生裸跑 → 升级率最高（教师介入最频繁），但每次升级只覆盖单步。此时轨迹 = "大量学生失败步骤 + 少量教师单步"，其可见错误信号密度最高。按 F7 的 Errors 轴，这条混合轨迹**最可能被闸门整体拒绝**——即教师那几步正确示范会连同学生的失败步骤一起被丢弃，进不了蒸馏。教师指导在系统最需要它的冷启动阶段，恰好最不可能转化为可用进料。
4. 这与已被接受入台账的"prompt 错配"是两件事：prompt 错配是措辞瑕疵（改了模板即可），而 provider 融合是**数据结构缺陷**（需要合成器/管线加 provider 标记与分臂拆解才能修）。设计方把两者都归为"模板瑕疵/澄清"是低估了后者。建议：合成阶段给每个 assistant 轮次打 provider 标记，管线在蒸馏前按 provider 拆分教师段与学生段，至少让"教师正确段"能作为独立进料。

## 三、对总体判断"闭环断裂"框定的表态

设计方立场：闭环未合拢是**已知阶段性状态**，文档病在时态未标注；正确结论是"文档未如实标注状态"而非"设计目标不可达"。

**我的裁定：接受该框定，附一条保留意见。**

接受的部分：round 1 的 17 项中，确实有大量"已设计未落地却以现在时书写"的时态问题（F8/F9/F10/F13/F17 等），修订后文档已用"现役/待建-演进编号"标注制修正，这是本轮最有价值的产出，我认可"文档病在时态"是主诊断。

保留意见：**"闭环断裂"不纯是时态病**。有三处断裂即便如实标注后仍是**设计层实质缺口**，且恰好是"学习是否发生"的承重墙：
1. **验证闸门的判别轴正交**（F7）——这不是标注问题，是闸门设计本身把"过程干净"当"经验有用"。
2. **非目标排除权重更新 ⇒ "学习"的因果对象只能是库，判据却用能力术语表述**（F2）——这是目标命题的措辞与物理现实不符，标注时态救不了。
3. **教师进料与错误步骤融合**（F14）——这是数据结构缺口，标注"待建三路合并"只说明了现状，未覆盖"当前单路进料连教师段都不可分离"这一更底层的缺陷。

因此我接受"阶段性状态"框定用于描述**归因奖惩/淘汰通道/三路合并**（它们确在 §5/§7 有立项）；但不接受该框定用于覆盖 **F2/F7/F14 三项**，它们不是"待合拢的环"，而是"环的承重墙本身有裂缝"。标注后文档仍应把这三点从"待建清单"中单列，视为**演进方案的前置设计问题**而非普通待办。
